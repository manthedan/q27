# KL KV-tolerance gate (whitepaper item 1)

Adopt the Bonsai whitepaper §4.4 methodology as a q27 gate: measure KV-
quantization damage as **per-position output forward-KL against the same
model's FP16-KV baseline**, not corpus NLL — isolating the KV effect from
weight quality (gate 3 could only disentangle by bucket-shape argument).

## Design

- **One process, one model mapping, two engines.** `MetalEngine::Shared`
  bundles what must exist once per artifact: the `Model` mmap, the
  `MetalBackend` (queue, pipelines, whole-mapping buffer + residency set),
  and the weight wrap. `MetalEngine::open_shared(path)` builds it; a new
  engine ctor takes the `shared_ptr<Shared>` plus per-engine `context` /
  `turbo3_kv`. The existing path-taking ctor delegates. Engine members
  `model_`/`backend_`/`weights_` become references into `Shared`, so the
  199 existing use sites do not change. Never two mappings, never two
  wired residency sets — the memory-safe policy sees one model load.
- **Interleaved teacher-forcing.** New `teacher_force_logits(tokens, count,
  out)`: encode one chunk (≤ 12 tokens; count 1 takes the serial path) at
  the engine's current position and read back the chunk's logits rows
  (12 × 970 KB max). The KL driver loops: chunk through engine A (fp16 KV),
  same chunk through engine B (turbo3 KV), per-position forward-KL on the
  CPU in double precision, discard logits. Both engines advance in
  lockstep; nothing weight-sized is ever copied.
- **`--kl-kv` CLI mode** rides the `--nll FILE --nll-long N` input path:
  builds the fp16 baseline and turbo3 engine from one `Shared`, reports
  per-position KL bucketed 0–2k / 2k–8k / 8k–16k / 16k–32k (same edges as
  the NLL buckets) plus overall mean nats.
- **`forward_kl(p_logits, q_logits, n)`** in `src/kl.h`: two logsumexp
  reductions then one accumulation pass, all double.

## Gates

1. `test-cpu`: `forward_kl` unit — KL(p,p) = 0, KL ≥ 0, agreement with a
   naive softmax reference, asymmetry sanity.
2. Plumbing gate (model): fp16-vs-fp16 self-KL over a 256-token slice must
   be exactly 0.0 at every position — two engines sharing one mapping run
   identical dispatch sequences, so any nonzero means the driver misaligned
   positions/chunks, not numerics.
3. The measurement: fp16 vs turbo3 over the 8K wikitext prefix (~2× one
   8K pass ≈ ~25 min on the mini). Reference points (their Table 6,
   off-policy): low-bit weights tolerate KV noise at 0.0011–0.0029 nats vs
   FP16 weights' 0.0137–0.222 — the claim to reproduce on turbo3 before
   trusting any sub-2-bit KV experiment.

## Non-goals

On-policy (own-generations) KL, sub-2-bit KV experiments, GPU KL reduction
(CPU double is ~1 min over 8K), CUDA parity — all follow-ups once the gate
exists.
