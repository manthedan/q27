# 3090 merged-server graph OOM — re-baseline, attribute, fix

Status: PRE-REGISTERED before measurement (results appended below the
line). Machine: yukon (RTX 3090 24 GB, CUDA 12.0, sm_86), Daniel-authorized
2026-07-16 night ("we have gpu time on yukon, run whenever you want").
Release blocker from the midday regate: the merged `q27-server` OOMs in
`cudaGraphInstantiate` (`verify_graph_w`, `spec_sample_graph`) at ctx 16384
AND 4096, where the Jul-14 prebuilt w8 fits at 23,224 MiB.

## What changed since the finding

- Upstream P3 merged (e72a28f): fused-verify round graphs behind
  `Q27_BATCH_GRAPH=1` (default OFF — should be footprint-neutral at
  default), conductor exec-cache priced by upstream at ~7.2 MB/exec,
  ~230 MB at the 32-cap. Re-baseline required before any fix work.
- Attribution instrument added this session: `Q27_GRAPH_TRACE=1` brackets
  every `cudaGraphInstantiate` in `build_spec_graphs` with `cudaMemGetInfo`
  and prints a per-family table (execs + MB); on a FAILED instantiate the
  table prints before abort, so the OOM run itself attributes.

## Open hypothesis the midday finding did not close

The midday verdicts never recorded the merged build's `Q27_W_MAX`. The
prebuilt that fits is a **w8** build; the source default is **12**, and the
in-tree comment prices the 8→12 graph zoo at ~1.5× captures plus one
~157 MB role set per width. If the midday build was w12-default, part or
all of the "footprint outgrew the card" is a build-width mismatch, not
upstream growth. Leg 1 settles this before anything else.

## Legs (in order; each may end the session early)

1. **Apples-to-apples w8 rebuild** (merged tree, `-DQ27_W_MAX=8`, sm_86):
   launch server at ctx 16384. If it FITS: record footprint vs 23,224 MiB,
   run the canonical gate — the release blocker reclassifies as
   "24 GB cards need the documented w8 build" and the fix is a
   Makefile/README note + upstream issue text. Legs 3+ become optional
   headroom work.
2. **Attribution runs**, `Q27_GRAPH_TRACE=1`, both widths (w8 fits-or-not,
   w12 expected-OOM): per-family MB tables. This is the evidence for the
   upstream issue either way.
3. **Fix (only if w8 also OOMs, or as opt-in headroom): lazy sampled
   family.** `spec_sample_graph` + `verify_sample_graph_w` launch only in
   the temperature>0 round; CC serving is greedy. Defer their
   capture+instantiate to first sampled request (mutexed, stream-synced,
   engine idle at that point by the slot model under `Q27_BATCH=0`).
   Kill line: if deferred capture is unsafe with live slots (capture-mode
   violation, cross-slot stall), fall back to env-gated skip
   (`Q27_SAMPLED=0` → temperature>0 requests get a clean 400) and record.

## Gates

- G1 (repro honesty): the OOM reproduces on the merged tree at w12 before
  any fix is claimed to matter; if it does NOT reproduce, record that the
  P3 merge or width was the whole story and stop.
- G2 (attribution sums): family table total accounts for ≥80% of the
  free-memory drop across `build_spec_graphs` (else the instrument is
  measuring allocator noise, not graphs).
- G3 (fit): the shipped configuration (w8, or w12+lazy if leg 3 runs)
  boots at ctx 16384 on the 3090 with headroom logged.
- G4 (identity): 16-token canonical gate byte-exact through the booted
  server (`metal_cuda_gate.py --cuda-ssh yukon`, compares live).
- G5 (sampled path, only if leg 3 lands): first temperature>0 request
  triggers the deferred build and completes; a second reuses it; greedy
  traffic before/after is byte-identical to a no-lazy control.
- G6 (restore): prebuilt w8 relaunched exactly as found (ctx 16384, port
  18080), health + live completion verified, footprint 23,224 MiB.
