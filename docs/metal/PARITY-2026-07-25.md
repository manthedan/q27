## Audit findings

### A1 — q4s/q5f/q6f are a loader **policy** gate, not a kernel gap (HIGH)

**Status: loader blocker REMOVED (`613cdf6`); tiers still UNVALIDATED here.**

The three newest tiers are all defined by a **single-Q4 `lm_head`**. The
Metal loader rejected them, but not for the reason the old parity doc
assumed ("nothing in `src/metal/` knows the dtype"). The machinery was
already there:

- `metal_engine.cpp:166-171` — `matrix_dtype_ok` for non-bonsai packs
  already accepts `Q4_G64` **or** `Q8_G128` **per layer matrix**. So q5f's
  `ffn_down`→Q8 and q6f's `ffn_gate`→Q8 promotions load as-is.
- `metal_engine.cpp:1209-1213` — `project()` routes both Q4 and Q8 to
  `matvec_quantized`; only bonsai (T2/B1) dtypes take the other path.
- `metal_engine.cpp:250-252` — `output_q4.weight`, the MTP draft head, is
  **required** to be `Q4_G64` at `{VOCAB, N_EMBD}` — the same shape as
  `output.weight` — and `:1696` projects it through that same path.

So Metal already loads, stores, and projects a Q4 vocab-sized head every
time MTP is on. The only blocker is the dtype **policy** gate at
`metal_engine.cpp:189-192`, which pins `output.weight`/`token_embd.weight`
to exactly `Q8_G128` for non-bonsai packs.

Why it matters: upstream measures **q5f as the best quality that fits a
24 GB card** (wikitext PPL 7.9491 — beats q4s, default, and q8, and matches
q6 at 2.3 GB less). This box is a 24 GiB M4. That tier is currently
unreachable on the Metal arm for a one-gate reason.

**What shipped.** The gate is load-bearing (codex P2: "a stray wrong-tier
matrix means a broken repack and must fail here, not compute silently"), so
the widening is scoped to that ONE tensor and to the Q-tier family only:
ternary/binary/mixed packs stay pinned via `require_tier`, and `token_embd`
stays pinned Q8 (no shipped tier moves it — it is a row lookup, not a GEMV
read), keeping its broken-repack check.

**Strictly additive:** for a Q8 head the old and new paths both accept, with
the same shape check, so no artifact that loaded before changes behavior and
the currently-served default tier is untouched by construction.

**Still UNVALIDATED end-to-end.** This removes the loader blocker; it does
not make the tiers supported. No canonical/NLL/task ladder has run against
q4s, q5f or q6f on Metal — that needs an artifact pull (~18 GB, none local)
plus the serialized GPU-exclusive slot. `docs/MODELS.md` was corrected in
the same commit: it had listed q4s as "supported" on Metal, which was never
true (the loader rejected it), and q5f/q6f were missing entirely. All three
now read "loads, UNVALIDATED on Metal", and the 20–24 GB recommendation no
longer names q4s. Top candidate for the next slot window.

### A2 — Metal is structurally immune to upstream's dangling-capture bug (guardrail)

Upstream `1a15ff8` item 1 was a genuine latent UB: `thinking` was read
by-reference out of a dead handler frame in **all three** CUDA SSE
providers, because those lambdas use `[&, samp, prompt, ...]` — a default
`&` capture that silently picks up anything not listed.

Metal's four providers (`metal_server.cpp:2406, 2554, 2880, 3310`) use
**explicit** capture lists with no default specifier
(`[&runtime, ids, n, sampling, ...]`). Any handler local read inside is a
compile error until it is listed. That is why Metal never had this bug —
and why adding `req_think` this round produced a clean build failure
instead of silent stack-layout luck.

Two consequences worth recording:

1. **Do not "simplify" an SSE capture list to `[&, ...]`.** The verbosity
   is the safety property.
2. The nested `[&, sock]` keepalive lambdas (`:2693, :3057, :3670`) are
   *not* an exception — they run synchronously inside `run()`, within the
   provider frame that owns what they capture.

### A3 — `/health` auth exemption is safe here (accepted, noted)

`/health` is exempt from the new API-key check so infra probes work
without the secret — every harness under `tools/` and
`deploy/runpod-serverless/handler.py` polls exactly that endpoint and
nothing else unauthenticated (verified).

`/health?identity=1` discloses `artifact_sha1` unauthenticated. Accepted:
it identifies a public artifact, and unlike upstream's `/health?verify=1`
(which *recomputes* resident-weight checksums, ~20 ms of unauthenticated
work per request) Metal's `resident_model_sha1()` is **cached** behind
`model_identity_mu` and returns 20 precomputed bytes
(`metal_server.cpp:682-694`). No amplification vector. Recorded so the
exemption is not widened to a route that does real work.

### A4 — Deliberate divergence: wrong-typed scalar handling

Upstream's `jnum`/`jint` read a **wrong-typed** field as absent. Metal
keeps rejecting those on `temperature`/`top_p`/`top_k`/`seed`/`max_tokens`
(codex branch-review P2, recorded at `sampling_params`): silently serving a
server default while the client believes its sampling settings were honored
is the worse failure. Only **null**-tolerance was adopted, which is the
part that breaks real clients.

Also worth stating plainly: Metal's exposure to this class was always a
**400**, never upstream's **500** — `guarded()`/`anthropic_guarded()` catch
`std::exception` into a typed `invalid_request_error` envelope
(`metal_server.cpp:2125` / `:2187`), where upstream's throws escaped into
httplib's 500 + `EXCEPTION_WHAT` handler. Same bug class, milder blast
radius.

### A5 — P16 prefix cache: convergent design, one real gap

Metal's `disk_snapshot_store.h` already implements P16a's core rule
**independently and earlier**: token-prefix keyed, filename is only a hash
that narrows the candidate set, and every load compares the stored token
vector against the request prefix before a byte of state is read. That is
the exact strict rule upstream adopted after CachyLLama shipped the cheap
hash-only version and had to patch it (2026-07-23).

- **P16b cross-conversation entry** — Metal's prefix matching is already
  "stored tokens are a prefix of this request", so a shared system block
  hits by construction.
- **P16c host-RAM tier** — architecturally N/A. Upstream's own measurement:
  the tier removes ~206 ms of *file read* from a ~245 ms restore, the other
  38 ms being the H2D import that unified memory does not have. On Metal
  the page cache already covers that read, and pinned host RAM buys
  nothing there.
- **P16c boot prefetch** — **built, measured, KILLED, removed.** The
  pre-registered kill line fired: A/B over a real 610 MB snapshot (n=3/arm)
  moved the first restore by +240 ms against 1386/3225 ms of within-arm
  spread — unresolvable. The trace gives the mechanism: the disk restore is
  **230 ms, 1.6 %** of the request; the other **98.4 % (14.57 s)** is the
  residual prefill of the 95 tokens the snapshot did not cover. Prefetch
  could remove at most 194 ms, ~1.3 % of what it exists to speed up. The
  flag and `prefetch_recent` were deleted per the kill line; the mechanism
  is recorded in
  [plans/2026-07-25-boot-prefetch.md](plans/2026-07-25-boot-prefetch.md).

  Two results worth more than the feature:
  - **The disk snapshot tier is worth far more on Metal than on CUDA**:
    **~64×** in steady state (~4.9 s to restore a 6912-token prefix + 95
    residual, vs ~312 s of cold prefill for a comparable prompt at
    55.7 ms/token). The ~21.8x first reported here was measured on *first*
    requests and was diluted by the A7 warm-up below. Prefill is
    memory-wall-bound on a base M4 (every chunk re-reads a 17 GB model over
    120 GB/s).
  - **A7 (new): the FIRST request in a fresh process pays ~9-10 s of
    one-time cost.** Isolated by trace — three identical disk-restore
    requests in one process cost 14009 / 5108 / 4857 ms at the same tier,
    hit and residual, so the gap belongs to *being first*, not to
    restoring. A 2-token "hi" request absorbs it (10362 ms), after which
    the big restore costs 4931 ms instead of 14081 ms. Leading hypothesis:
    first-touch page-in of the mmap'd ~17 GB artifact (~6 s at 2.8 GB/s)
    plus lazy PSO builds. One fix attempted and **measured as not working**
    (a boot-time `engine.step()` cost 10 s and saved nothing — the decode
    path is not what needs warming); reverted, not shipped. Full record:
    [plans/2026-07-25-first-request-warmup.md](plans/2026-07-25-first-request-warmup.md).
    NOTE: this corrects the first framing of A7, which blamed residual
    prefill / chunk granularity — ruled out, since the steady-state cost of
    that identical 95-token residual is 4.6-4.7 s.

### A8 — the snapshot write holds the GPU lease (from upstream `77a6ac5`)

All three `save_disk_snapshot` call sites (`metal_server.cpp:1325, 1365,
1400`) sit directly under `auto gpu=lease_now()`, and the write itself is
inside `engine.save_state()`. So the **entire disk write holds the GPU
lease**. Measured on this box during the A5/A7 runs: `snapshot_save` →
`outcome` was **7234 ms** for a 610 MB entry, and the in-tree comment
already records "+~15 s under the lease" for ~1.3 GB.

At `--slots 1` that is invisible. The shipped default is `--slots 2`, where
one slot's snapshot write stalls the other slot's decode for those seconds.
The existing comment frames this cost as *write churn* (bounded by the LRU
budget); upstream's `77a6ac5` reframes it correctly as **a restore waiting
on a write**, and fixes it by giving the persist writer its own staging
buffer so the two never contend.

The CUDA fix shape does not port directly — their pinned `pfx_stage` /
`pfx_wstage` pair exists because a D2H copy must land somewhere before the
write. On unified memory there is no D2H copy: the snapshot bytes are
already CPU-addressable, so the Metal fix is simply to take the bytes under
the lease and do the file write outside it (the store header already states
the intended rule — "All file I/O runs OUTSIDE the GPU lease; only
save_state/load_state ... go under it" — which `save_state` currently
violates by doing both).

Not implemented: it changes the lease/threading model on a serving branch
and needs the GPU slot to gate (two-slot interleave under a save). Filed.
